## 1. 문서 개요
- 목적: 도메인 정의서(1-domain-definition.md)에 정의된 엔티티·규칙·유스케이스를 제품 관점(범위, 일정, 기술스택, 비기능요구사항)에서 구체화하여 2일 내 MVP 개발의 실행 기준을 제공한다.
- 대상 독자: 1인 개발자(본인), 향후 참여 가능한 개발자/리뷰어.
- 본 문서는 도메인 규칙을 재정의하지 않으며, 상세 엔티티/상태/규칙은 항상 1-domain-definition.md를 참조한다.

## 2. 목표 및 배경
- 비즈니스 목표: 개인 할일 관리 웹앱을 최소 기능으로 빠르게 출시하고, 1000명 동시 접속을 견디는 구조로 설계한다.
- 목표 사용자: 학생, 20대~50대 직장인. 개인용 할일/카테고리 관리가 필요한 일반 사용자.
- 배경: 카테고리는 Admin이 전역 관리하고 사용자는 선택만 하는 구조로, 관리자와 일반 사용자의 역할이 명확히 분리된 서비스.

## 3. 범위

### 3.1 MVP 범위 (2일 내 구현, Must Have)
- 회원가입 / 로그인(인증), 로그아웃
- 회원정보 수정(본인)
- Todo 등록/조회/수정/삭제(제목, 메모, 시작일/종료일, 카테고리 선택)
- Todo 상태 파생 표시(시작전/진행중/완료/지연) 및 완료 토글
- Todo 목록 필터링(카테고리별, 상태별)
- Admin: 회원 목록 조회
- Admin: Category 등록/수정/삭제, 기본 Category 자동 재할당(삭제 시)
- 기본적인 권한 검증(401/403), 입력 유효성 검증(startDate ≤ endDate 등)
- 반응형 웹 UI(PC/모바일 브라우저 대응)

### 3.2 확장 범위 (MVP 이후, Out of Scope)
- Admin의 타 회원 Todo/정보 직접 수정·삭제(도메인 정의서 9장 미정 항목)
- 기본 Category 삭제/수정 정책 확정(도메인 정의서 9장 미정 항목)
- 알림/리마인더, 검색, 정렬 고도화, 페이지네이션 UX 개선
- 비밀번호 재설정 이메일 발송
- 소셜 로그인(Google/Kakao 등 OAuth 연동)
- 이메일 인증 방식(가입 시 실제 이메일 소유 여부 확인, 인증메일 발송·인증 완료 전 로그인 제한 등)
- 관리자 대시보드/통계, 감사 로그
- 접근성(a11y) 대응, 다국어(i18n)
- 캐시 계층(Redis) 등 성능 고도화, 로드밸런싱/오토스케일링 인프라
- Refresh Token 서버측 무효화/블랙리스트(로그아웃 즉시 강제 만료, 탈취 대응)

## 4. 기술 스택 및 아키텍처 개요

### 4.1 스택
- 프론트엔드: React 19 + TypeScript, Zustand(전역 상태: 인증/UI), TanStack Query(서버 상태: Todo/Category/User 동기화 및 캐싱), 레이어 구조는 FSD(Feature-Sliced Design, app/pages/widgets/features/entities/shared) 적용(상세는 5-project-principle.md 참조)
- 백엔드: Node.js + Express(JavaScript), pg(node-postgres) 직접 사용 — ORM/Prisma 미사용, SQL/쿼리빌더 직접 작성
- DB: PostgreSQL 17
- 인증: JWT 기반, Access Token(단기, 예: 15분) + Refresh Token(장기, 예: 7일) 조합. Access Token 만료 시 Refresh Token으로 재발급. 비밀번호는 bcrypt 해시 저장

### 4.2 아키텍처 방향 (실용적 수준, 1000명 동시접속 고려)
- 단일 Express 서버 + PostgreSQL 단일 인스턴스로 시작. 과도한 마이크로서비스 분리 없음(1인 개발/2일 일정 특성상 모놀리식 유지).
- pg Pool을 이용한 커넥션 풀링(예: max 20 내외)만 적용 — 별도 PgBouncer 등 외부 풀러는 MVP에서 제외.
- 자주 조회되는 컬럼(todo.user_id, todo.category_id, users.email unique)에 기본 인덱스만 적용. 복합 인덱스/파티셔닝 등은 트래픽 확인 후 추후 검토.
- Todo 상태는 저장하지 않고 조회 시 파생 계산(도메인 정의서 5장) — 별도 배치/스케줄러 불필요.
- 상태 비저장(stateless) API 서버(JWT 인증)로 설계하여 필요 시 수평 확장(Express 인스턴스 추가)이 용이하도록 함. MVP 단계에서는 실제 다중 인스턴스 배포는 하지 않음.
- 캐시(Redis)는 MVP 범위 제외. 응답 지연이 실측되면 확장 범위에서 도입 검토.

## 5. 기능 요구사항 (도메인 정의서 7장 유스케이스 기반)

### 5.1 일반 사용자(Member)
| 기능 | 설명 | 근거 |
|---|---|---|
| 회원가입/로그인 | id는 이메일 형식(정규식 형식 검증만, 실제 메일 수신 가능 여부·인증메일 발송은 하지 않음)으로 입력받고, 회원 id 목록 내 중복 여부만 점검. 비밀번호 기반 로그인, 인증 실패 처리. 로그인 성공 시 Access Token + Refresh Token 발급. 소셜 로그인·이메일 인증(실제 소유 확인)은 3.2 확장범위 참조 | 도메인 6장 규칙1, 8장 예외 |
| 토큰 재발급 | Access Token 만료 시 Refresh Token으로 재발급(재로그인 없이 세션 연장) | - |
| 로그아웃 | Refresh Token 무효화(클라이언트 토큰 폐기, MVP는 서버측 블랙리스트 미구현) | - |
| 회원정보 수정 | 본인 정보만 수정 가능 | 도메인 6장 규칙2 |
| Todo 등록 | Category 선택(미지정 시 기본), 시작일/종료일, 메모, 하루 여러 건 허용 | 도메인 6장 규칙4·7 |
| Todo 조회/필터 | 카테고리별/상태별(시작전/진행중/완료/지연) 필터링 | 도메인 6장 규칙8 |
| Todo 수정/삭제 | 소유자 본인만 가능 | 도메인 6장 규칙2 |
| 완료 토글 | 완료/미완료 전환 시 상태 재계산 | 도메인 5장 |

### 5.2 관리자(Admin)
| 기능 | 설명 | 근거 |
|---|---|---|
| 회원 목록 조회 | 전체 회원 목록 조회(수정/삭제 권한은 범위 밖) | 도메인 6장 규칙9 |
| Category 등록/수정/삭제 | 전역 Category 관리, 일반 사용자는 조회/선택만 | 도메인 6장 규칙3 |
| Category 삭제 시 재할당 | 삭제 대상 Category를 참조 중인 Todo는 기본 Category로 자동 재할당 | 도메인 8장 예외 |

## 6. 비기능 요구사항
- 성능/동시접속: 1000명 동시 접속 상황에서 정상 응답(타임아웃/장애 없이 처리). pg Pool 및 기본 인덱스로 대응, 추가 인프라는 MVP 범위 제외.
- UI: 반응형 웹 UI 필수(모바일/태블릿/PC 브라우저에서 레이아웃 대응). 별도 모바일 앱 없음.
- 보안: 비밀번호 해시 저장, JWT(Access+Refresh Token) 인증, 소유권 검증(403), 미인증 접근 차단(401), 기본적인 입력 유효성 검증(SQL 인젝션 방지를 위해 파라미터 바인딩 쿼리 사용). Refresh Token은 httpOnly 쿠키로 저장해 XSS를 통한 탈취 위험을 낮춘다.
- 접근성(a11y): 본 프로젝트에서는 고려하지 않음(명시적 범위 제외).
- 유지보수성: 도메인 정의서와 PRD 간 용어/규칙 일관성 유지, 코드는 라우트-서비스-쿼리 계층 정도로만 단순 분리(과도한 레이어링 지양).

## 7. 일정 및 마일스톤 (2일)

- DB 스키마 설계 및 마이그레이션(users, categories, todos), 기본 인덱스 적용
- 인증(회원가입/로그인/JWT Access+Refresh Token 발급 및 재발급 API), 회원정보 수정 API + 화면

- Admin 회원 목록 조회 화면
- 반응형 UI 마무리, 권한/유효성 검증 점검(401/403, startDate≤endDate 등)
- 통합 테스트 및 배포 준비

## 8. 리스크 및 제약사항
- 1인 개발 + 2일 일정: 테스트 커버리지·문서화·예외 케이스 검증에 할애할 시간이 제한적 → MVP 범위를 엄격히 준수하고 확장 범위는 착수하지 않음으로써 완료 가능성 확보.
- Prisma 미사용(순수 SQL/pg): 스키마 변경·쿼리 작성 속도가 ORM 대비 느릴 수 있음 → 초기 스키마를 단순하게 유지(3개 테이블)하고 마이그레이션 스크립트를 최소화하여 리스크 완화.
- 1000명 동시접속 목표 대비 실제 부하 테스트는 2일 일정상 생략 → 커넥션 풀 크기 및 기본 인덱스만으로 목표를 설정하고, 실측 검증은 추후 과제로 명시.
- 도메인 정의서상 미정 항목(기본 Category 삭제/수정 여부, Admin의 타 회원 데이터 직접 수정 권한)은 MVP에서 구현하지 않음 → 확정 전까지 관련 기능 요청 발생 시 범위 협의 필요.

## 9. 도메인 정의서와의 연결
- 본 PRD의 모든 기능/규칙은 `docs/1-domain-definition.md`의 엔티티(User/Category/Todo), 관계(4장), 상태 규칙(5장), 비즈니스 규칙(6장), 유스케이스(7장), 예외 케이스(8장), 요구사항 추적 매핑(9장)을 기준으로 한다.
- 규칙/엔티티 상세 정의가 필요한 경우 항상 도메인 정의서를 우선 참조하며, 본 문서는 이를 제품/일정/기술 관점에서 구체화한 문서로 유지한다.
