## 문서 개요
- 목적: 일반 사용자(Member) 관점에서 MVP 범위 기능의 실제 사용 흐름을 단계별로 정의하여 화면/API 설계 및 테스트 기준으로 활용한다.
- 범위: PRD 3.1 MVP 범위 중 일반 사용자 기능. 확장 범위(PRD 3.2, 예: 소셜 로그인, 이메일 인증, Refresh Token 서버측 무효화)는 각 시나리오 말미에 "향후 확장"으로만 짧게 언급한다.

## 시나리오 1. 회원가입

**Precondition**
- 사용자는 미가입 상태이며 회원가입 화면에 접근했다.

**Main Flow**
1. 사용자가 이메일 형식의 id, 비밀번호, 이름을 입력하고 가입 요청을 제출한다.
2. 시스템은 id의 이메일 형식 여부를 정규식으로 검증한다(실제 메일 수신 가능 여부는 확인하지 않음).
3. 시스템은 기존 회원 id 목록 내 중복 여부를 확인한다.
4. 시스템은 비밀번호를 bcrypt로 해시하여 저장하고, role=Member로 계정을 생성한다.
5. 시스템은 가입 완료를 응답하고 로그인 화면으로 이동시킨다.

**Alternative/Exception Flow**
- 2a. 이메일 형식이 아니면: 형식 오류 메시지를 반환하고 가입을 거부한다.
- 3a. 이미 존재하는 id로 가입 시도 시: 중복 이메일 오류를 반환하고 가입을 거부한다(도메인 8장).

**Postcondition**
- 신규 User(role=Member)가 생성되고, 사용자는 로그인 가능한 상태가 된다.

**향후 확장**: 소셜 로그인(OAuth), 실제 이메일 소유 확인(인증 메일)은 MVP 이후 확장 범위(PRD 3.2).

## 시나리오 2. 로그인

**Precondition**
- 사용자는 가입된 계정을 보유하고 있으며 로그인 화면에 접근했다.

**Main Flow**
1. 사용자가 id(이메일)와 비밀번호를 입력하고 로그인을 요청한다.
2. 시스템은 저장된 해시와 입력 비밀번호를 대조해 인증한다.
3. 인증에 성공하면 시스템은 Access Token(단기)과 Refresh Token(장기)을 발급한다.
4. Refresh Token은 httpOnly 쿠키로 저장되고, Access Token은 클라이언트에 전달된다.
5. 시스템은 로그인 성공 응답과 함께 사용자를 메인(Todo 목록) 화면으로 이동시킨다.

**Alternative/Exception Flow**
- 2a. id 또는 비밀번호가 불일치하면: 인증 실패 오류를 반환하고 로그인을 거부한다. 이때 계정 존재 여부는 노출하지 않는다(도메인 8장).

**Postcondition**
- 사용자는 인증된 상태(Access/Refresh Token 보유)로 앱의 모든 기능에 접근 가능해진다.

---

## 시나리오 3. 토큰 재발급 (Access Token 만료 시)

**Precondition**
- 사용자는 로그인 상태이며 Access Token이 만료되었으나 Refresh Token은 유효하다.

**Main Flow**
1. 클라이언트가 만료된 Access Token으로 API를 호출하면 시스템이 401을 반환한다.
2. 클라이언트는 자동으로 Refresh Token(쿠키)을 이용해 토큰 재발급을 요청한다.
3. 시스템은 Refresh Token의 유효성(서명/만료)을 검증한다.
4. 검증 성공 시 새로운 Access Token을 발급하여 응답한다.
5. 클라이언트는 새 Access Token으로 원래 요청을 재시도한다.

**Alternative/Exception Flow**
- 3a. Refresh Token이 만료되었거나 유효하지 않으면: 401을 반환하고 재로그인을 요구한다(로그인 화면으로 이동).

**Postcondition**
- 사용자는 재로그인 없이 세션이 연장되어 계속 앱을 사용할 수 있다.

**향후 확장**: 서버측 Refresh Token 무효화/블랙리스트(탈취 대응)는 MVP 이후 확장 범위(PRD 3.2).

---

## 시나리오 4. 로그아웃

**Precondition**
- 사용자는 로그인 상태이다.

**Main Flow**
1. 사용자가 로그아웃을 요청한다.
2. 시스템은 클라이언트가 보유한 Access Token을 폐기하고, Refresh Token 쿠키를 만료 처리한다.
3. 시스템은 로그인 화면으로 이동시킨다.

**Alternative/Exception Flow**
- 없음(단순 클라이언트측 토큰 폐기, MVP는 서버측 블랙리스트 미구현).

**Postcondition**
- 사용자는 미인증 상태가 되며, 이후 인증이 필요한 기능 접근 시 401과 함께 로그인 화면으로 유도된다(도메인 8장).

---

## 시나리오 5. 회원정보 수정

**Precondition**
- 사용자는 로그인 상태이며 본인의 회원정보 수정 화면에 접근했다.

**Main Flow**
1. 사용자가 이름 등 수정 가능한 항목을 변경하고 저장을 요청한다.
2. 시스템은 요청자의 Access Token에서 userId를 확인하고, 수정 대상이 본인 정보인지 검증한다.
3. 검증 통과 시 시스템은 정보를 갱신하고 완료를 응답한다.

**Alternative/Exception Flow**
- 2a. 미인증 상태로 접근 시: 401 반환, 로그인 화면으로 유도(도메인 8장).
- 2b. 타인의 정보를 수정하려는 시도가 감지되면(요청 파라미터 조작 등): 403 권한 없음 처리(도메인 6장 규칙2, 8장).

**Postcondition**
- 본인의 회원정보가 갱신된 상태로 저장된다.

## 시나리오 6. Todo 등록

**Precondition**
- 사용자는 로그인 상태이며 Todo 등록 화면에 접근했다. Admin이 등록한 Category 목록을 조회할 수 있다.

**Main Flow**
1. 사용자가 제목, 메모, 시작일/종료일(캘린더 선택)을 입력하고 Category를 목록에서 선택한다(선택 안 하면 미지정).
2. 사용자가 등록을 요청한다.
3. 시스템은 startDate ≤ endDate 여부를 검증한다.
4. Category가 지정되지 않았으면 시스템은 전역 '기본' Category를 자동 지정한다.
5. 시스템은 완료 여부(completed=false) 상태로 Todo를 생성하고 요청자(userId)를 소유자로 기록한다.
6. 시스템은 등록 완료를 응답하고 목록에 반영한다.

**Alternative/Exception Flow**
- 3a. startDate > endDate이면: 유효성 오류를 반환하고 등록을 거부한다(도메인 6장 규칙6, 8장).
- 2a. 같은 날짜(구간)에 이미 다른 Todo가 존재해도 등록을 허용한다(도메인 6장 규칙7, 1일 다건 허용).

**Postcondition**
- 신규 Todo가 사용자 소유로 저장되며, 조회 시 상태(시작전/진행중)가 파생 계산되어 표시된다.

---

## 시나리오 7. Todo 조회 및 필터링(카테고리별/상태별)

**Precondition**
- 사용자는 로그인 상태이며 본인의 Todo 목록 화면에 접근했다.

**Main Flow**
1. 시스템은 요청자(userId) 소유의 Todo만 조회한다.
2. 시스템은 각 Todo의 completed 값과 오늘 날짜를 startDate/endDate와 비교해 상태(시작전/진행중/완료/지연)를 파생 계산한다(도메인 5장).
3. 사용자가 카테고리 필터 또는 상태 필터(시작전/진행중/완료/지연)를 선택한다.
4. 시스템은 해당 조건에 맞는 Todo만 재조회하여 목록에 표시한다.

**Alternative/Exception Flow**
- 1a. 미인증 상태로 접근 시: 401 반환, 로그인 화면으로 유도(도메인 8장).
- 필터 조건에 해당하는 Todo가 없으면 빈 목록을 표시한다(오류 아님).

**Postcondition**
- 사용자는 본인 소유 Todo 중 선택한 카테고리/상태 조건에 맞는 목록을 확인한다.

---

## 시나리오 8. Todo 수정

**Precondition**
- 사용자는 로그인 상태이며 본인 소유의 Todo 편집 화면에 접근했다.

**Main Flow**
1. 사용자가 제목/메모/시작일/종료일/Category 중 일부를 변경하고 저장을 요청한다.
2. 시스템은 해당 Todo의 소유자가 요청자 본인인지 검증한다.
3. 시스템은 변경된 startDate/endDate에 대해 startDate ≤ endDate 여부를 검증한다.
4. 검증 통과 시 시스템은 Todo를 갱신하고(updatedAt 갱신) 완료를 응답한다.

**Alternative/Exception Flow**
- 2a. 소유자가 아니면: 403 권한 없음 처리(도메인 6장 규칙2, 8장).
- 3a. startDate > endDate이면: 유효성 오류를 반환하고 수정을 거부한다(도메인 6장 규칙6, 8장).

**Postcondition**
- 해당 Todo의 내용이 갱신되고, 목록/조회 시 재계산된 상태로 반영된다.

---

## 시나리오 9. Todo 삭제

**Precondition**
- 사용자는 로그인 상태이며 본인 소유의 Todo가 존재한다.

**Main Flow**
1. 사용자가 목록 또는 편집 화면에서 특정 Todo의 삭제를 요청한다.
2. 시스템은 해당 Todo의 소유자가 요청자 본인인지 검증한다.
3. 검증 통과 시 시스템은 Todo를 삭제하고 완료를 응답한다.
4. 목록에서 해당 Todo가 즉시 제거된다.

**Alternative/Exception Flow**
- 2a. 소유자가 아니면: 403 권한 없음 처리(도메인 6장 규칙2, 8장).

**Postcondition**
- 해당 Todo가 영구 삭제되어 이후 조회에서 나타나지 않는다.

---

## 시나리오 10. Todo 완료 토글

**Precondition**
- 사용자는 로그인 상태이며 본인 소유의 Todo가 목록에 표시되어 있다.

**Main Flow**
1. 사용자가 목록에서 특정 Todo의 완료 체크(토글)를 클릭한다.
2. 시스템은 해당 Todo의 소유자가 요청자 본인인지 검증한다.
3. 시스템은 completed 값을 반전(false→true 또는 true→false)시켜 저장한다.
4. 시스템은 completed와 오늘 날짜/startDate/endDate 비교를 통해 상태를 재계산한다(완료 해제 시 시작전/진행중/지연 중 하나로 재분류, 도메인 5장).
5. 목록에 갱신된 상태가 즉시 반영된다.

**Alternative/Exception Flow**
- 2a. 소유자가 아니면: 403 권한 없음 처리(도메인 6장 규칙2, 8장).

**Postcondition**
- Todo의 완료 여부가 전환되고, 파생 상태가 최신 값으로 목록/필터 결과에 반영된다.
